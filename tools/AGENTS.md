# Repo tooling, CI, and releases

Private tooling lives under `tools/<role>/<domain>/{src,tests}`; Steiger enforces the layout and kebab-case domain names. Every tool is a workspace named `@open-pencil/<domain>-tools`, listed literally in the root `workspaces` (the manifest schema rejects globs on purpose), so it can declare dependencies and run through `bun --filter`. `bun run check:tools` type-checks every tool through `tools/tsconfig.json`, reporting only files under `tools/` as `check:test-types` does for tests (`tools/checks/test-types/src/index.ts`); `bun run test:tools` runs every tool with a `test` script. A tool imports its own files through its package.json `imports` alias (`#ci/*`, `#release/*`), other tools through their package name, and the docs site config through the shared `#docs-config/*` path.

| Role        | Contract                                                                                                                      | Domains                                                                                                                              |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `checks/`   | Read the tree and exit non-zero; never write inside the repository                                                            | `architecture`, `lint`, `i18n`, `secret-scan`, `type-shapes`, `docs`, `package-quality`, `bundle-budget`, `workflows`, `dockerfiles` |
| `generate/` | Write generated files or artifacts, idempotently                                                                              | `brand`, `demo`, `emoji-metrics`, `tauri-menu`, `authoring-reference`, `visual-oracles`, `landing-posters`                           |
| `release/`  | Build, verify, and publish packages and native artifacts                                                                      | `package-artifacts`, `release-packages`, `fork-releases`                                                                                              |
| `ci/`       | Consumed by workflows: path classification and gate policy, container images, the review-guidance bot, Cloud deployment steps | `policy`, `images`, `pr-review-guidance`, `cloud-deploy`                                                                             |
| `dev/`      | Test running, benchmarks, and local services for humans                                                                       | `unit-tests`, `navigation-benchmark`, `dev-server`, `cloud`                                                                          |

- `checks/bundle-budget` owns `check:bundle`, the gzipped startup budget; it reads the last build's Vite manifest, so `preview-build.yml` runs it after `bun run build`.
- Nothing under `generate/` or `release/` runs from `bun run check` except through a check entrypoint; `generate/authoring-reference` keeps its `check.ts` beside `generate.ts` until it splits.
- Resolve the workspace with `resolveWorkspaceRoot` from `@open-pencil/package-artifacts-tools`, not parent-directory traversal. Keep sibling imports relative.
- `dev/unit-tests` owns the shard map and runner (`tests/AGENTS.md`).
- No `scripts/` entrypoints: root `package.json` scripts call tool files directly.

## CI

- A workflow or action step runs one line of shell; anything more is a tested script under `tools/` the step calls (`bun run check:workflows`). Steps set up Bun, the install, LFS files, and package builds through `.github/actions/setup/workspace`.
- Third-party actions are pinned to a commit with its version in a comment, which Dependabot keeps current (`.github/dependabot.yml`); the Code quality job lints workflows with actionlint and audits them with zizmor (`.github/zizmor.yml`), and a suppression carries its reason beside it.
- Dockerfiles share one style. hadolint parses and lints each in the Code quality job (`.hadolint.yaml`; warnings fail, and a suppression is an inline `# hadolint ignore=` with its reason), which covers how apt is used. `bun run check:dockerfiles` adds what hadolint does not, on `dockerfile-ast`: `# syntax=docker/dockerfile:1`, then a comment saying what the image is for and who uses it, and every base image as `name:tag@sha256:digest`. Only the Dev Container, which each developer builds from its file, pins apt versions; a CI image is pinned by its digest where it is used, and rebuilding it brings its packages' security updates. Dependabot refreshes base digests, never their versions (`.github/dependabot.yml`).
- CI images live in `tools/ci/images/<name>/Dockerfile`, are built by `.github/workflows/image-<name>.yml`, and publish `ghcr.io/open-pencil/<name>-ci`, tagged with the Ubuntu release and the commit; jobs use them by digest. `native-contracts` runs the native app contract tests on Ubuntu 24.04; `native-release` is the Linux desktop release build's Ubuntu 22.04, with the libraries the AppImage bundles and the Rust toolchain `rust-toolchain.toml` pins (`ARG RUST_TOOLCHAIN`, held to it by the check), and its workflow bundles the app in every build of it before a release may pin it.
- `.github/workflows/ci.yml` and `ci-heavy.yml` define validation gates. PR CI always classifies changed paths through `tools/ci/policy/src/policy.ts`: root docs, package READMEs, every `AGENTS.md`, `packages/docs` Markdown and assets, and skill Markdown are docs-only; runtime prompt Markdown, executable examples, configuration, and unknown paths require code validation.
- Docs-only changes run documentation integrity and the docs build; everything else runs the full suites (`tools/ci/policy/src/policy.ts`).
- The Cloud suites run when a change touches what `packages/cloud` is built from, derived from its workspace dependencies (`tools/ci/policy/src/cloud-inputs.ts`).
- The aggregate `CI result` gate requires successful classification and every applicable job; failures, cancellations, and unexpected skips cannot pass (`tools/ci/policy/src/gate.ts`).
- Do not restore workflow-level path filtering on required CI: a required check whose workflow never runs stays pending and blocks the merge (`.github/workflows/ci.yml`).
- `commitlint.config.ts` enforces commit structure in the **Commit messages** job; the separate **PR title** workflow validates titles. Preserve the `Release vX.Y.Z` and `Release vX.Y.Z-beta.N` exception, including the ` (#N)` the merge queue appends, and product casing when changing rules; the known AI co-author check does not rewrite base history. Gate policy lives in `tools/ci/policy/src/policy.ts`.
- `tools/ci/policy` runs right after Bun is set up, before any install, so it imports only Node built-ins; `oxlint.json` switches `@open-pencil/data/prefer-es-toolkit` off there (`.github/workflows/ci.yml`, the `changes` job).
- The commitlint formatter, `tools/ci/policy/src/commit/annotations.ts`, is the exception: it runs inside `check:commits`, after install (`tools/ci/policy/tests/commit/annotations.test.ts`).
- Other CI tools install their workspace first. `pr-review-guidance.yml` does so without a local action, since a review runs its workflow file from the pull request over the default branch's checkout (`.github/workflows/pr-review-guidance.yml`).
- Required checks must also run on `merge_group`, the merge queue's event; read base and head from `merge_group.base_sha`/`head_sha` there (`ci.yml`, `pr-title.yml`).
- Path classification measures a pull request from its merge commit's first parent, the base as it is now; `pull_request.base.sha` lags when the base moves and would count the base's newer commits as the pull request's (`tools/ci/policy/tests/classify.test.ts`).
- A passing pull request run records the tree it tested as the `CI verified tree` status on the PR head; a merge queue commit with that exact tree is classified `verified` and runs only the always-on checks. Any other tree, including a group with other PRs ahead, gets the full run (`tools/ci/policy/src/verified-tree/`).
- The app production workflow runs on `v*` tags, and the docs workflow when a release is published, since the download page reads GitHub's releases at build time; both also run on `workflow_dispatch`, never on ordinary `master` pushes. `build.yml` checks the tooling out under `.pipeline/` and runs `tools/release/release-packages` from there.

## Releases

- Update versions in the root and publishable package manifests plus `desktop/tauri.conf.json` and `desktop/Cargo.toml`; run `bun run changelog:assemble`, curate `Unreleased` (`bun run check:changelog --release`), and move it into `## x.y.z — YYYY-MM-DD`; commit `Release vX.Y.Z`; tag and push `vX.Y.Z`. A pre-release uses `X.Y.Z-beta.N` throughout.
- `.github/workflows/build.yml` is the source of truth: `v*` tags (or dispatches for an immutable stable tag) build shared frontend/package outputs once, build signed desktop artifacts in parallel, verify and attest one complete same-run artifact set, publish npm packages, and replace the draft release assets using the exact changelog section. Policy, provenance, and recovery: `tools/release/release-packages/README.md`.
- A binary a release ships with Rust crates compiled in carries their third-party notices: each is listed in `NOTICED_ARTIFACTS` (`tools/release/release-packages/src/notices/artifacts.ts`), the release job writes the notices with cargo-about before `prepare`, accepting the licenses the crate's `deny.toml` allows, and `pack` refuses a package without them (`tools/release/release-packages/tests/notices/artifacts.test.ts`).
- The editor's build writes `THIRD-PARTY-NOTICES.md` for the npm packages it bundles, the service worker's Workbox packages included, with `rollup-plugin-license`, and fails on a license outside its allowlist (`vite/third-party-notices.ts`). The shared frontend archive refuses to form without it and the desktop Rust notices, and every stable desktop bundle carries both under `licenses/`; a release tag from before a kind of notice is built without it (`tools/release/release-packages/tests/native/frontend.test.ts`).
- `.github/workflows/release-chromium.yml` builds OpenPencil Chromium (Tauri v3 with CEF), a flavor of a release, by hand from `build/tauri-v3` once that branch has merged exactly the release tag, and adds its macOS bundles and `latest-chromium.json`, its update feed, to that release after every macOS build succeeds; stable tooling and the download page skip those files (`isChromiumAsset`). Its steps live in `tools/release/release-packages/src/chromium`, beside the stable release scripts they reuse.
- Public workspace packages are discovered by the package-artifacts catalog. Bun source exports require the complete `src` directory in package contents; Node exports use `dist`. Release preparation must preserve resolution maps. Prepared publish directories receive the root `LICENSE` when a package has none of its own, and every package needs a `README.md` because npm renders it. Publishing uses prepared npm tarballs verified through the shared Node/Bun consumer checks; never publish package directories manually. `test:packages` first runs the packaging guards in `tools/checks/package-quality/src/smoke/guards.ts`: fixture manifests packed with the real `npm pack` that must trip the tarball inspector and the Node/Bun consumer checks before those checks vouch for real packages.
- Pre-releases are only `vX.Y.Z-beta.N`: they publish to npm's `next` dist-tag, draft as a GitHub pre-release that is never latest, install on Windows as MSI `X.Y.Z.N`, and skip the app and docs deploys (`tools/release/release-packages/src/version.ts`).
- A beta's changelog section opens with the pre-release note and lists changes since the previous beta. The final `X.Y.Z` replaces its beta sections with one section written against the previous stable release, opened by a short highlights paragraph, with fixes to new features folded into their bullets; the GitHub pre-releases keep the beta notes (`CHANGELOG.md`).
- Official builds (`VITE_OPENPENCIL_FEEDBACK=on`) emit hidden source maps; `deploy-app.yml` and the `build.yml` frontend job inject PostHog chunk IDs, upload the maps to PostHog error tracking as release `openpencil@<version>`, and strip them from `dist`, and `build.yml` attaches them as `OpenPencil_<version>_sourcemaps.tar.gz`. Both need the `POSTHOG_CLI_API_KEY` secret, a personal key with error tracking write and organization read (`tools/release/release-packages/src/sourcemaps/publish.ts`).
- Ensure Tauri and Apple signing/notarization secrets are configured. Verify the draft title, body, and artifacts, then publish. Release titles are exactly the tag (`vX.Y.Z`) without a product-name prefix.
- Homebrew's `openpencil` cask is managed upstream: BrewTestBot proposes bumps and Homebrew merges them. Check the upstream cask PR after publication; do not push to the archived custom tap or add bump automation. Users install the app with `brew install --cask openpencil` and the CLI through npm or Bun.

## Forks

OpenPencil keeps forks of dependencies it builds into WebAssembly: Skia's CanvasKit (`open-pencil/skia`) and Taffy (`open-pencil/taffy`). They all work the same way, so a new one follows them.

- A fork's patches are commits on a branch named `openpencil/<name>`, listed in the branch's `OPENPENCIL.md`, each one also proposed upstream; a workflow on that branch builds every push and releases it as `<name>-<commit>` with the built files, `THIRD-PARTY-NOTICES.md`, and `SHA256SUMS` (`.github/workflows/openpencil.yml` on `open-pencil/taffy`).
- A fork's `openpencil/<name>` branch changes only through pull requests against it, reviewed as one here is, by CodeRabbit and then a maintainer, since every push to it is a release; a package pins only a release of a merged commit. Each fork's branch carries an `AGENTS.md` with its own build, test, and upstreaming rules (`open-pencil/taffy`, `open-pencil/skia`).
- A package here ships a fork's build by pinning one release in `release.json` (repository, tag, and each file's SHA-256) and never builds it: `bun install`'s `postinstall` and the package's `build` fetch it into `dist/`, keeping files that match their pins, and CI caches those `dist/` folders by the pins (`tools/release/fork-releases/tests/fetch.test.ts`, `.github/actions/setup/workspace/action.yml`).
- Moving a package to a new release is `bun run fork:pin packages/<name> <name>-<commit>`, which takes the files and hashes from the release's `SHA256SUMS`; moving Taffy also moves the `rev` of the `[patch]` in the root `Cargo.toml`, which patches its source into the Cargo workspace for Blitz, to the same commit, so HTML import and auto layout share one Taffy (`tools/release/fork-releases/tests/pin.test.ts`).
- A fork's build is third-party code in the editor's bundle: its package's license and the fork's `THIRD-PARTY-NOTICES.md` go into the app's notices, though it is a workspace package (`forkNotices` in `vite/third-party-notices.ts`).

## Demo document

How the `/demo` tour is structured and built: `packages/docs/development/demo-tour.md`.

- The tour is built from `tools/generate/demo` into the ignored `public/demo.fig` and opened like any `.fig` file; never generate it in the browser (`tools/generate/demo/src/ensure.ts`).
- A chapter that needs something new from the engine adds that package's `src` to the fingerprint `ensureDemoDocument` rebuilds on; `bun run generate:demo` forces a rebuild (`tools/generate/demo/src/ensure.ts`).
- Bind every color in the tour, icons included, to the Theme and App chrome collections, whose Dark and Light modes `src/app/demo/theme.ts` switches by name (`tools/generate/demo/src/document/theme.ts`).
- Shader stills need the Playwright Chromium with WebGPU; without it the build skips them, and only an editor in a browser with WebGPU draws the frames when the demo opens (`tools/generate/demo/src/shaders/stills.ts`).

## Landing posters

`tools/generate/landing-posters/` captures WebP stills of every docs landing stage, per locale, theme, and layout, from a production docs build served locally in headless Chromium with software WebGL. `build:production` in `packages/docs` runs it after `vitepress build`; it reuses `.cache/landing-posters/<fingerprint>` when the inputs in `src/fingerprint.ts` are unchanged and copies the stills into `dist`, and `generate:landing-posters` forces a capture. The docs deploy workflow spreads the capture over runners: one job runs `build:site`, four run the generator with `--shard i/4`, and the deploy job gathers their stills and runs it with `--assemble`, which fails on any missing still; dispatching it with `dry-run` builds and captures without deploying and keeps the stills as an artifact. A stage that starts depending on a new source tree adds it to `LANDING_POSTER_INPUTS`.

## Brand assets

Canonical artwork lives in `assets/brand/` (main mark and optical micro master; see its README). `tools/generate/brand/` derives web, docs, and native icons with RealFaviconGenerator and Tauri; generated assets are ignored, not committed. Vite and VitePress configs prepare their own targets, and Tauri dev/build hooks prepare native icons.
